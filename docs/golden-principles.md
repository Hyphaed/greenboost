# Golden principles

The invariants every change to GreenBoost must hold — encoded once here,
enforced mechanically by `checks/` (see the "enforcing check" column), and
linked from `AGENTS.md` so they survive a fresh clone even though
`CLAUDE.md` (the fuller, rule-dense version an operator maintains locally)
stays untracked. When a principle and the code disagree, the code is wrong,
not this document — but if this document goes stale, update it in the same
change that changes the rule.

| # | Principle | Rationale | Enforcing check | Escape hatch |
|---|---|---|---|---|
| 1 | **Never hardcode a hardware-shaped value.** VRAM/RAM/pool sizes, per-card thresholds, device counts, bandwidth figures — always `%`-derived from the executing node's own detected topology (`gb_topology.py`), never copied from a reference box. | GreenBoost runs on machines with wildly different hardware; a host-tuned literal (e.g. an 11 GB VRAM budget) silently OOMs on an 8 GB feeder — a real, live incident (2026-07-13) that motivated this rule. | `checks/check_hardware_literals.py` | Add to `checks/allowlists/hardware.txt` with a one-line justification comment (wire-protocol sizes, kernel page/hugepage constants, and similar true physical constants are pre-allowlisted). |
| 2 | **Every subsystem emits dataflux telemetry AND is MCP-queryable.** A placement/scheduling/eviction/actuation decision with no dataflux trace is a gap to close, not an acceptable silence. | The dataflux log is the flight recorder; an LLM (or a human) diagnosing GreenBoost must never have to `grep` a log file that isn't in the flight recorder. | `checks/check_dataflux_coverage.py` (advisory→blocking) | Add the module to `checks/allowlists/dataflux_exempt.txt` with a reason (e.g. "pure library, no scheduling decisions"). |
| 3 | **Installer/uninstaller parity.** Every file, wrapper, venv, systemd unit, or MCP registration Full Install creates, Full Uninstall (purge) must remove. A fresh `git clone` + Full Install must reproduce the exact polished behavior of a working live system. | The wizards are pillar columns of the project — drift here means "works on my machine" silently rots into "doesn't work on a fresh box." | `checks/check_installer_parity.py` | Add a reviewed exception to `checks/allowlists/install_manifest.txt` with a reason (e.g. "generic glob already covers this file, no explicit purge line needed"). |
| 4 | **GPU compute always; CPU tensor compute is forbidden.** Every allocation path (Path A DMA-BUF, Path B cuMemHostRegister) keeps weights/KV on a GPU-compute-ready path. CPU is only for non-tensor work (I/O, accounting, topology detection, prefetch scheduling). | The whole point of GreenBoost is GPU-accelerated inference at more VRAM than physically exists — falling back to CPU tensor compute defeats that. | Manual review (no automated check yet — a static check would need to trace tensor placement through the shim, out of scope for `checks/` today). | None — this is a hard architectural boundary, not a tunable. |
| 5 | **Fill every GPU to ~90% (Rule #1).** VRAM is the fastest tier; DDR (T2) and NVMe (T3) exist only for the genuine overflow that doesn't fit the ~90% target, never as a substitute for VRAM that's physically free. A single oversize allocation must be SPLIT (front-load), never dumped whole into a slower tier while VRAM sits idle. | Live incident (2026-07-12): 17.5 GB weights → T2 while ~8 GB VRAM sat physically free (`vram_headroom_mb=244`) — the exact violation this rule exists to catch. | `dataflux_critic`'s `rule1_underfill` transition (live-telemetry check, not a static one — see `gb_dataflux.py:_detect_transitions`). | None — the 10% headroom itself is the only tunable (`GB_VRAM_FRONTLOAD_PCT`), and it stays %-derived per principle 1. |
| 6 | **Quality-first tiering: T3 is never for speed-critical data.** The planner gives every component the highest precision that fits (bf16 > int8 > int4/nvfp4); dropping below fp8 requires an explicit, surfaced quality tradeoff, never a silent choice. | Speed and quality are both goals — the project's `quant_advisor`/`optimize_inference` explicitly rank fp8-and-above options first and hide below-fp8 options unless `allow_below_fp8=True`. | `quant_advisor`'s `meets_fp8_floor` field (self-reporting, not yet a standalone static check). | `allow_below_fp8=True` with the `quality_tradeoff` field surfaced — never silent. |
| 7 | **All optimization logic lives in the layer, consumers stay thin.** `gb_quant.py`/`gb_llm.py`/`gb_attn.py`/`gb_placement.py` own every placement/quant/attention decision; ai-forge (and any other pipeline) only calls in, never re-implements the logic locally. | A consumer that reimplements quant/placement logic drifts from the canonical version the first time either side changes (confirmed drift: `ai-forge/forge/gpu.py`'s hand-ported `shim_env` admits exactly this in its own comments). | `checks/check_docs.py`-style grep for duplicated logic is aspirational; today enforced by code review + `workflow/porting-reference.md`'s "reuse, don't duplicate" notes. | None. |
| 8 | **Importing the backend must never touch the GPU.** All device work is lazy (`LazyDeviceTensors`); no import-time `torch.cuda.*` call. This is what makes the layer loadable under the LD_PRELOAD shim and on CPU-only boxes. | An eager CUDA call at import time breaks the shim's ability to intercept allocation calls before the real CUDA runtime initializes. | Manual review (a static AST check for `torch.cuda` calls outside function bodies is a reasonable future `checks/` addition). | None. |
| 9 | **Secrets, real IPs, and developer home paths never land in tracked files.** No live tokens, no `192.168.x.x`-shaped LAN IPs, no `/home/<user>/` absolute paths in anything `git` tracks. | A pre-push leak of a HuggingFace/GitLab token or a real LAN topology is a security incident, not a style nit. | `checks/check_secrets.py` (mechanizes the CLAUDE.md pre-push checklist: live-secret regex, real-IP regex, home-path regex, tracked-AI-cache-file check). | Secret TOKEN matches: none, ever. IP/home-path matches: `checks/allowlists/secrets_reviewed.txt`, exact `path:line` only (never a glob) — for the real false-positive class of illustrative doc/CLI examples and synthetic test fixtures that use an IP/path *shape* without identifying real infrastructure. Every entry must be individually read before adding. |
| 10 | **UI commands follow the snapshot/TUI/`--llm` paradigm.** Every status/diagnostic command (`vitals`, `proton-logs`, `cluster`, etc.) isolates its rendering into a `_cmd_<name>_snapshot()`, runs an alt-screen TUI loop only when interactive, and always supports a compact `--llm` machine-readable mode with ANSI stripped. | An agent driving GreenBoost via `--llm` output must get the same information a human sees in the TUI, in a form it can parse without scraping ANSI codes. | Manual review today (a `checks/` static check could grep for the `_cmd_*_snapshot` naming convention on any new UI command — a reasonable future addition). | None. |
| 11 | **Resolve GreenBoost's own state through GB-Semantics, never a raw field, when a governed metric/segment exists.** Every question about VRAM fill, tier pressure, quant quality, tok/s, or cluster health goes through `semantic_resolve`/`semantic_answer`/`semantic_segments` (or `gb_semantics.py` directly) first; a raw dataflux/telemetry field is the fallback ONLY, and the answer must say so. | Several raw fields mean two different things depending on where they're read (shim-inflated vs. physical VRAM; a 0/1/2 enum vs. a 0.0-1.0 fraction under the same field name) — each has already produced a real wrong answer in this project's history. `semantics/metrics.yaml`'s `never_use` entries document the traps by name. | `checks/check_semantics_coverage.py` (every metric/segment has a real resolver/evaluator + owner; `source_fields` against a known dataclass must be real) + `tests/test_semantics_evals.py` (40-entry trap-weighted eval set, pinned to a frozen fixture, with a governed-vs-ungoverned comparison per trap). | A metric/segment that genuinely doesn't exist yet — falls back to a raw field, but the answer's provenance must carry `governed: false` visibly, never presented with the same confidence as a governed one. |

## Adding a new principle

1. State it here, in the same terse, falsifiable form as the table above.
2. Name the mechanical check that enforces it — write one if none exists and
   the principle is checkable without deep semantic understanding of the code.
3. Update `AGENTS.md`'s one-line pointer if the principle is significant
   enough to surface in the map.
4. If the principle can never be fully automated (like #4 and #8 above),
   say so honestly in the "enforcing check" column rather than inventing a
   check that only pattern-matches the easy 80% of violations.
